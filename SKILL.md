# SKILL.md — Operating This Repo as an AI Agent

This file is for an AI agent (or a human moving fast) about to run scripts,
edit files, or open a PR in this repo. It is not a tutorial — see
[README.md](README.md) for that. It is a set of hard constraints and the
verified facts behind them. See also [CONTEXT.md](CONTEXT.md) for the
reasoning, and [CHANGELOG.md](CHANGELOG.md) for what's changed.

## Before touching this repo

Run through this in order. Every item is a real, current check — verify it
yourself if you don't trust this file's freshness.

1. **Confirm you're in WSL2 (Debian), not native Windows Git Bash or
   PowerShell.** `podman-compose.yml`'s `network_mode: host` is a
   WSL2-specific workaround for a netavark/nftables limitation, and the rest
   of the toolchain — `podman`, the pinned `tfsec` path, `curl`/`jq` in the
   shell scripts — has only been validated on WSL2. Running these scripts
   natively on Windows is untested territory, not a supported path.
   (This applies to *local, manual* script runs. CI's `scan`/`deploy-local`
   jobs run on GitHub-hosted `ubuntu-latest` and install their own
   Podman/tfsec fresh per run — see CONTEXT.md. `auto-fix.yml` is the only
   workflow still on the WSL2 `floci-self-hosted` runner.)
2. **Check tfsec version.** `tfsec --version` must print exactly `v1.28.5`.
   `scan.sh` and the CI pipeline both hard-fail (exit 2 / `exit 1`) on any
   other version — don't work around that check, fix the binary.
3. **Check floci-core is up.** `podman ps --filter "name=floci-core"`. If
   empty: `podman-compose -f podman-compose.yml up -d`. `deploy.sh`,
   `verify.sh`, and `drift-check.sh` all hard-fail if `localhost:4566` isn't
   reachable.
4. **Check floci-az is up, if doing any Azure work.**
   `podman ps --filter "name=floci-az"`. If empty and you need Azure's
   sidecar-spawning services (Functions/AKS/Redis/ACR): use
   `scripts/start-floci-az.sh`, not a plain `podman-compose up -d` — see
   the next item for why.
5. **The netavark/iptables fix must be applied host-side, not via a
   container env var.** `floci-az`'s Functions/AKS/Redis/ACR services
   spawn sidecar containers over a mounted Docker socket; this WSL2 host's
   netavark backend needs `NETAVARK_FW=iptables` set on the **host-side**
   `podman.service` process's environment, via
   `systemctl --user set-environment` — a container's own `environment:`
   block is a completely separate process tree from that host-side process
   and can't reach it, by construction (see `podman-compose.yml`'s
   `SEC_INTENT` comment on the `floci-az` service). `scripts/
   start-floci-az.sh` applies the real fix; a plain `podman-compose up -d`
   does not, and Azure sidecar-spawning services will hit an nftables
   error without it.
6. **`pipeline.yml` does NOT call `grow-stack-azure.sh` yet.** Azure's
   growth loop (`scripts/grow-stack-azure.sh` + `growth-queue-azure.yaml`)
   is proven to run correctly locally, but nothing in CI invokes it — don't
   assume it's running on a schedule just because AWS's `grow-stack.sh` is.
   See CONTEXT.md § Growth loop.
7. **Check the fixture state before assuming a gate result.**
   `./scripts/toggle-fixture.sh status`. If it reports `on`, `scan.sh` is
   *supposed* to fail — that's not a bug for you to fix.
8. **Never hand-edit `terraform/modules/security/main.tf`,
   `main.tf.with-fixture`, or `main.tf.without-fixture` directly.** Use
   `toggle-fixture.sh {on|off}` to change state, or
   `bootstrap-fixture-snapshots.sh` to regenerate the snapshots after a
   deliberate edit. Both run `terraform validate` before touching disk for
   real; a plain `cp`/editor save skips that safety check.
9. **Never hand-write anything under `dashboard/public/data/*.json`.** Those
   10 files are machine-generated by `scan.sh` / `deploy.sh` / `verify.sh` /
   `drift-check.sh` / `agent-loop.sh`. If you need fresh demo data, run the
   real script.
10. **Never run `git push` yourself for dashboard data.** That's
    `sync-dashboard.sh`'s job, and only its job — see the gate below.
11. **Treat `AWS_ACCESS_KEY_ID=test` / `AWS_SECRET_ACCESS_KEY=test` as the
    only valid credentials anywhere in this repo.** If you see anything
    matching a real AWS key prefix (`AKIA`, `ASIA`, `AIDA`, `ANPA`, `ANVA`,
    `APKA`, `ASCA`) in an env var, a file, or a diff — stop. Don't run
    `deploy.sh` or `agent-loop.sh` until it's gone.
12. **Check `.github/CODEOWNERS` before expecting a PR to merge unreviewed.**
    `terraform/`, `terraform/modules/security/`, `scripts/scan.sh`,
    `scripts/toggle-fixture.sh`, `scripts/deploy.sh`, `scripts/agent-loop.sh`,
    `scripts/ai/`, and `.github/` all require `@arifbazli` review — no
    exceptions, including PRs opened by the `floci-agent-loop` bot.
13. **Never reorder or delete entries in `growth-queue.yaml` once a
    scheduled run may have applied them.** `scripts/grow-stack.sh` finds
    "next" purely by diffing the queue against `terraform state list` — an
    address's dependencies must stay earlier in the list than the address
    itself. Also don't collapse the `growth-state-${{ github.run_id }}` +
    prefix `restore-keys` cache-key pattern in `pipeline.yml` into one
    static key — `actions/cache` entries are immutable per key, so a single
    static key can never be "updated," it just silently stops persisting.

## Tool pins

| Tool | Pinned version | Enforced by |
|---|---|---|
| `tfsec` | **1.28.5** | `scan.sh` (`required_tfsec="v1.28.5"`, exits 2 on mismatch); `.github/workflows/pipeline.yml`'s `scan` job installs this exact release binary fresh on `ubuntu-latest`, then verifies it, every run |
| `terraform` | 1.9.8 | Documented only — not version-checked in code |
| `jq` | 1.7.1 | Documented only (`--rawfile` used elsewhere in the toolchain) |
| `podman-compose` | 1.6.0 (local WSL2) | Documented only. **CI note:** confirmed via a real CI run — `deploy-local` installs Podman **4.9.3** and podman-compose **1.0.6** from `ubuntu-latest`'s apt repo, not version-pinned in CI, and not the same major versions as local dev (Podman 5.x / podman-compose 1.6.0). |

> [!CAUTION]
> **Do not upgrade tfsec past 1.28.5.** 1.28.10 has a confirmed regression:
> `tfsec:ignore:` directives are silently dropped. That's not cosmetic here —
> the deliberate misconfig fixture (`AVD-AWS-0057`) is the thing the whole
> gate demo depends on being caught. A newer tfsec could silently let it
> through with no error, no warning, just a clean scan on a repo that isn't
> actually clean.

Install:
```bash
mkdir -p ~/.local/bin
curl -fsSL https://github.com/aquasecurity/tfsec/releases/download/v1.28.5/tfsec-linux-amd64 \
  -o ~/.local/bin/tfsec && chmod +x ~/.local/bin/tfsec
tfsec --version 2>&1 | grep "1\.28\.5" || echo "WRONG VERSION"
```

## The agent-loop.sh allowlist

Verbatim, from README's Security controls table:

> Agent (`agent-loop.sh`) allows only: `podman restart floci-core` and
> `terraform apply` (safe drift + gate PASS). Never edits `*.tf`, never
> destroys.

The full allow/deny list, verbatim from the script's own header
(`scripts/agent-loop.sh` lines 17–27):

```
ALLOW:  podman restart floci-core
        terraform apply -auto-approve
        terraform state snapshot to .bak file
        cat / jq / cp / mv any file in the dashboard/data directory
DENY:   anything that modifies *.tf files
        terraform destroy
        terraform apply if the plan changes security-tagged resources
        anything that exits the agent-loop's own process
        anything that writes to /tmp/*.tf
```

If you're extending `agent-loop.sh`, any new action must fit inside `ALLOW`
above or it doesn't belong in this script — open a separate, explicitly
human-reviewed script instead (see CODEOWNERS).

Before it applies anything, the loop re-checks two independent gates every
iteration, not just once at startup:
- `drift-last.json` classification must be `"safe"` — `destructive` and
  `security_only` are refused.
- `tfsec-last.json` gate must be `"PASS"` — any open HIGH/CRITICAL freezes
  drift reconciliation entirely (restart still allowed).

## sync-dashboard.sh credential gate

`sync-dashboard.sh` is the **only** script in this repo permitted to run
`git push`, and only for `dashboard/public/data/`. Before it commits
anything, it scans the staged diff for these patterns (verbatim from the
script, lines 96–104) and refuses (exit 3) if any match:

```
AKIA[0-9A-Z]{16}                                  # AWS access key id
ASIA[0-9A-Z]{16}                                  # AWS session token
AROA[0-9A-Z]{16}                                  # AWS role id
cfut_[0-9a-zA-Z_-]{20,}                            # Cloudflare API token
BEGIN (RSA |EC |OPENSSH |DSA |PGP )?PRIVATE KEY
aws_secret_access_key
api_key[[:space:]]*[:=][[:space:]]*["']?[A-Za-z0-9]{16,}
password[[:space:]]*[:=][[:space:]]*["']?[A-Za-z0-9!@#$%^&*()_+=-]{8,}
arn:aws:[a-z0-9-]+:[a-z0-9-]*:[0-9]{12}:           # real AWS ARN — see allowlist below
```

The one allowlisted exception: ARNs under the floci dummy account,
`arn:aws:*:*:000000000000:*`. Anything else matching an `arn:aws:` shape
with a different 12-digit account ID is treated as a leak.

Two more hard stops, independent of the pattern list:
- Every staged file must parse as valid JSON (`jq -e .`) — a truncated write
  is refused, not pushed half-finished.
- Any staged file over 1MB is refused outright.

And before any of that: if `git status --porcelain` shows changes **outside**
`dashboard/public/data/`, the script exits 2 without staging anything. It
will not partially commit — either everything staged is dashboard JSON, or
it stops.

| Run the bounded agent | `scripts/agent-loop.sh` | `LOOP_INTERVAL`/`MAX_LOOPS` env overrides |
| Triage tfsec findings | `scripts/ai/triage.py` | MEDIUM/LOW only; never the fixture |
